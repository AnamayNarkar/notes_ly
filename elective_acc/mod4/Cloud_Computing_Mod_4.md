### PART A: 4.1 LARGE-SCALE ML SERVICE ON CLOUDS

### T1. Large-scale ML service on cloud: concept, need, architecture

**Definition.** A cloud-based system that provides the computing power, storage, data-processing tools and ML software needed to train, deploy and operate ML models on very large datasets. Instead of buying and maintaining powerful servers, organisations rent infrastructure that scales up or down with the workload.

**Why cloud is needed.**
- The dataset is several TB/PB, with millions or billions of training records.
- Deep-learning models are complex and may need hundreds of CPUs/GPUs.
- Many users may request predictions at the same time.

Cloud supplies, in order: large storage, distributed processing, GPU/TPU computing, model training, deployment, predictions.

**Diagram to draw (basic architecture):**

```
          USERS / APPLICATIONS
                  |
         +-------------------+
         |  ML Prediction    |
         |  Service (API)    |
         +-------------------+
                  |
             Trained Model
          /              \
   Model Training     Model Monitoring
         |
 +--------------------+
 | Distributed ML     |
 | Training Cluster   |
 | CPU / GPU / TPU    |
 +--------------------+
         |
 +--------------------+
 | Large-scale Data   |
 | Cloud Storage      |
 +--------------------+
         ^
 +--------------------+
 | Data Collection &  |
 | Preprocessing      |
 +--------------------+
```

**Exam format:** 5M = definition, why cloud (3 points), diagram. In 10M, add components T2 to T8.

### T2. Data storage and preprocessing

**Data storage.** Cloud storage holds images, videos, text, sensor data, customer transactions, logs and training datasets. Examples are Amazon S3, Google Cloud Storage and Azure Blob Storage. The data can be accessed by many compute nodes at once.

**Data preprocessing.** Raw data cannot be fed straight into an ML algorithm. It must be cleaned, filtered, transformed, normalised, labelled and converted to a suitable format. For very large datasets the preprocessing is distributed across machines.

**Diagram (from slide 7):**

```
        1 TB Dataset
              |
   +----+----+----+----+
   |Node|Node|Node|Node|      each node preprocesses its share
   +----+----+----+----+
              |
      Processed Dataset
```

This reduces preprocessing time. [SG] A rough illustration: if one node needs 8 hours for the 1 TB, four nodes ideally need about 2 hours.

---

### T3. Distributed ML and parallel model training

**Idea.** Instead of training on a single machine, many machines (workers) train together. Each worker performs part of the computation.

```
          Dataset
             |
   +---------+---------+
   |         |         |
Worker 1  Worker 2  Worker 3
GPU/CPU   GPU/CPU   GPU/CPU
   |         |         |
   +---------+---------+
             |
       Model Parameters
             |
        Updated Model
```

**Parallel training.** Cloud platforms provide CPUs, GPUs, TPUs, high-speed networking and distributed memory/storage.

**Numerical (from notes).** Training takes 100 hours on 1 GPU. On 20 GPUs the ideal time is 100/20 = **5 hours**. In practice it takes longer because of communication and synchronisation overhead.

**Extension [SG] (use as a worked example):**
- Speedup S = T1/Tn and efficiency E = S/n.
- If the real time on 20 GPUs is 8 hours, then S = 100/8 = 12.5 and E = 12.5/20 = **62.5%**.
- The lost 37.5% is overhead (communication, stragglers, synchronisation).

**[SG] Two ways to distribute.**
- *Data parallelism:* every worker holds a full copy of the model and trains on a different slice of the data, and the gradients are combined.
- *Model parallelism:* the model is split across workers because it is too big for one device.
- Worker updates are combined through a parameter server or collective communication (all-reduce). Slide 35 of 4.2 mentions "Parameter Server / Collective Communication".

### T5. Auto scaling (elasticity)

**Definition.** The cloud automatically increases or decreases resources according to demand. This is elasticity, one of the main advantages of cloud-based ML.

**Diagram and numbers (slide 13, 59, 60):**

```
Normal traffic:  100 requests/min     -->  2 ML servers
Peak traffic:    10,000 requests/min  -->  20 ML servers
Traffic falls:   20 servers --> 5 servers
```

A fixed number of servers would waste resources at low traffic and fail at peak.

**Example workload (slide 59):** morning 1,000 requests/min, afternoon 10,000, night 500. Low traffic uses 2 instances, high traffic 20, and when traffic drops 20 falls back to 5.

**Related PYQ:** D22 "Compare scalability and elasticity" (solved in Section 4).

**[SG] Numerical.** Suppose one inference server handles 500 requests/min.
- Servers needed = ceil(load / capacity).
- At 10,000 requests/min: 10,000/500 = 20 servers.
- At 3,000 requests/min: 6 servers.
- With a 70% target utilisation: 10,000/(500 x 0.7) = 28.6, so **29 servers**.

|---|---|---|

| Example | 10 million customer records -> ML model -> 10 million predictions | User request -> ML model -> prediction |
| Latency | Not critical | Very low, critical |
| Used for | Customer analysis, fraud analysis, recommendation generation, large-scale data processing | Fraud detection, speech recognition, image recognition, chatbots, recommendation systems |

### T7. Fault tolerance

Large-scale ML may use hundreds or thousands of machines, so some will fail. Cloud ML systems provide:
- Checkpointing
- Task restart
- Data replication
- Worker replacement
- Automatic recovery

```
Worker 1 --+
Worker 2 --+
Worker 3 --+--> Training          Worker 3 fails (X)
Worker 4 --+                            |
                                  New worker starts
                                        |
                                  Training continues
```

This prevents the whole training job from restarting. Example (slide 87): training is 40% complete and a GPU server fails, so the job resumes from the last checkpoint instead of the beginning.

**[SG] Checkpoint trade-off.** Frequent checkpoints lose less work after a failure but cost more I/O time. Rare checkpoints are cheap but risk losing hours of training.

**Related PYQ:** MJ21 Q1(A)(V) matching Reliability, Availability, Serviceability (solved in Section 4).

### T8. Machine Learning as a Service (MLaaS)

Cloud providers offer ML capabilities as a service. The user does not manage physical servers, GPUs, operating systems, networking or storage infrastructure. The user focuses on data, algorithms, model training, evaluation and application development.

| Provider | Platform |
|---|---|
| Amazon Web Services | SageMaker |
| Google Cloud | Vertex AI |
| Microsoft Azure | Azure Machine Learning |

[SG] Exam tip: relate MLaaS to the cloud service models. It is a higher-level service, similar to PaaS/SaaS, because the provider manages the infrastructure and tooling.

### T9. Advantages and challenges

**Advantages (8):**
1. Scalability
2. Cost efficiency (pay for what you use)
3. High computational power (GPU/TPU)
4. Large storage (object storage)
5. Faster training (distributed)
6. High availability (redundancy, fault tolerance)
7. Easy deployment (model exposed via APIs)
8. Elasticity (automatic scaling)

**Challenges (6):**
1. Data transfer: moving huge datasets is slow and expensive.
2. Communication overhead: workers exchange parameters.
3. Cost: GPU/HPC resources are expensive.
4. Security: sensitive training data must be protected.
5. Model management: many versions to store and monitor.
6. Resource management: efficient allocation of CPU, GPU, memory, storage. This leads into the second half of 4.1.

### RESOURCE MANAGEMENT FOR PRODUCTION-SCALE ML

### T11. Concept and importance

**Definition.** Efficiently managing the computing, storage, networking, memory, GPUs/CPUs, data and software resources needed to develop, train, deploy and operate ML models at large scale. A small experiment can run on a laptop. A production system may need hundreds or thousands of GPUs, TB/PB of data and thousands of requests per second.

**Goal:** use the right amount of resources at the right time while keeping performance, reliability, scalability and cost reasonable.

**Why important.** Example: an e-commerce recommender with 50 million users, millions of products, TBs of training data and 100,000 prediction requests per second. Without management:
- Training becomes very slow.
- GPUs remain idle.
- Memory becomes insufficient.
- Prediction latency rises.
- Servers get overloaded.
- Cloud costs become very high.
- The system may fail at peak traffic.

### T12. Types of resources and compute management

```
                    ML Resources
                         |
      +------------------+------------------+
      |                  |                  |
   Compute            Storage            Network
   CPU/GPU            Dataset            Bandwidth
   Memory             Models             Latency
      |
 Software Resources: Containers, Frameworks, Libraries, APIs
```

**Compute resources:** CPU, GPU, TPU, RAM, virtual machines, containers, Kubernetes clusters.

**Matching workload to resource (slide 31):**

| Workload | Suitable resource |
|---|---|
| Data preprocessing | CPU |
| Feature engineering | CPU |
| Traditional ML (e.g., logistic regression) | CPU |
| Deep learning | GPU/TPU |
| Model inference | CPU/GPU |
| Large LLM training | Multiple GPUs |

**Avoid both extremes.** Under-utilisation means GPU capacity of 100% with only 20% used, which wastes money. Over-utilisation means the workload is 100%+, which causes performance problems.

**CPU management.** CPUs handle data preprocessing, feature extraction, data loading, inference, API handling, scheduling and monitoring. Example: a job using 8 GPUs but only 2 CPU cores for preprocessing makes the GPUs wait for data. Better CPU allocation keeps GPUs supplied.

**GPU management: the platform must decide five things:**

| Decision | Meaning and example |
|---|---|
| How many GPUs | Job A image classification 1 GPU, Job B large neural net 4 GPUs, Job C LLM training 8 GPUs; check availability, then allocate |
| Which GPU type | GPUs differ in compute performance, memory, bandwidth, energy, cost; a very powerful GPU for a small job adds cost without benefit |
| How to share | Shared (Job A 40% + Job B 60% of one GPU) improves utilisation; dedicated (GPU1 to A, GPU2 to B) gives predictable performance |
| Which job gets priority | 2 GPUs free, 3 jobs: Job B (production retraining) high, Job A (research) medium, Job C (low-priority experiment) low |
| When to release | Training starts 10:00, GPU allocated 10:00, finishes 12:30, released 12:30, available to others 12:31; a GPU kept reserved after the job ends sits idle and wastes money |

**Related PYQ:** MJ21 Q2 OR "Compare GPU and CPU chips..." (solved in Section 4).

### T13. Memory management

- **Main memory (RAM):** data preprocessing, feature engineering, model loading, intermediate calculations.
- **GPU memory:** model parameters, activations, gradients, batches. If the GPU does not have enough, you get **Out Of Memory (OOM)** and the training may fail.

**Numerical (slide 42):**

```
GPU memory   = 16 GB
Model        = 10 GB
Batch data   =  8 GB
------------------------
Required     = 18 GB   >  Available = 16 GB   -->  OOM
```

**Fixes:** smaller batch size, model optimisation, gradient accumulation, mixed precision, larger-memory GPUs.

**[SG] Worked solution.** Assuming batch memory scales with batch size, halving the batch to 4 GB gives 10 + 4 = 14 GB, which fits in 16 GB. To keep the effective batch size, use 2 gradient-accumulation steps.

### T14. Storage and data management

**Storage holds:** raw data, processed data, training/validation/test datasets, model files, model versions, logs and monitoring data.

```
Raw Data -> Processed Data -> Training Dataset -> Validation Dataset -> Test Dataset
 -> Model Files -> Model Versions -> Logs and Monitoring Data
```

Cloud object storage (S3, GCS, Azure Blob) is the common choice. **Considerations:** capacity, read/write speed, cost, data durability, availability, access frequency.

**Data management.** The system continuously receives user, sensor, transaction, image, video, log, text and IoT data. It must collect, store, clean, transform, label, partition and feed data to the models. Large datasets use distributed processing (Large Dataset split to Workers 1-3, then Processed Dataset).

**Related PYQ:** A25 Q5(iii) Amazon S3 (solved in Section 4).

### T15. Network resource management

During distributed training, GPUs 1-4 exchange updates to synchronise parameters. Large amounts of data move between workers.

```
GPU 1 --+
GPU 2 --+
GPU 3 --+--> Parameter Synchronization
GPU 4 --+
```

Resource management must consider network bandwidth, latency, data-transfer cost, congestion and communication overhead. High-speed networking becomes particularly important for large distributed models.

---

### T16. Scheduling, allocation, isolation

**Scheduling.** The scheduler decides which job runs when and where. It considers priority, resource requirements, deadline, cost, fairness and availability.

**Numerical (slide 50, 51):** the cluster has 16 GPUs. Job A needs 8, Job B needs 4, Job C needs 8.
- A (8) + B (4) = 12 GPUs, leaving 4 free.
- C needs 8, so it **waits** until enough resources are available.
- [SG] Utilisation at that moment is 12/16 = 75%.

**Allocation** means deciding how much resource each workload gets. Giving 8 GPUs to a job that needs 2 wastes resources.

**Numerical (slide 52):**

| Job | CPU | GPU | Memory |
|---|---|---|---|
| Data preprocessing | 16 | 0 | 32 GB |
| Model training A | 32 | 4 | 128 GB |
| Model training B | 16 | 2 | 64 GB |
| Model inference | 8 | 1 | 32 GB |
| **Total [SG]** | **72** | **7** | **256 GB** |

**Isolation.** Multiple teams share one cloud ML cluster. One workload should not consume everything and hurt the others. It is achieved by containers, Kubernetes namespaces, resource limits (CPU, memory), GPU allocation and quotas.

**Quota example (slide 54):** Team A max 8 GPUs, Team B max 4, Team C max 4. The total is 16, matching the 16-GPU cluster.

### T17. Containers and Kubernetes

**Containers.** ML applications are packaged in containers (for example Python + TensorFlow/PyTorch + ML model + dependencies). Containers provide isolation, reproducibility, portability, resource limits and easier deployment. A container can be given limits such as CPU = 4 cores, Memory = 16 GB, GPU = 1.

**Kubernetes.** It manages containers and workloads for large production ML. It can schedule workloads, restart failed containers, scale applications, allocate CPU/memory, manage GPUs, provide service discovery and perform rolling deployments.

```
          Kubernetes Cluster
                 |
    +------------+------------+
    |            |            |
  Node 1       Node 2       Node 3
    |            |            |
  Pod A        Pod B        Pod C
    |            |            |
  ML API      Training      ML API
```

**[SG] Container vs VM (for a compare question).** A container shares the host OS kernel and is lightweight, starts in seconds and has less isolation. A VM carries a full guest OS and is heavier, starts slower and has stronger isolation.

**Related PYQ:** D22 Q5(i) Dockers and Containers (solved in Section 4).

### T18. Training resource management and hyperparameter tuning

**Pipeline and the resource each stage needs (slide 61, 62):**

```
Dataset -> Preprocessing -> Feature Engineering -> Training -> Validation -> Hyperparameter Tuning -> Best Model
```

| Stage | Resource |
|---|---|
| Preprocessing | CPU + RAM |
| Training | GPU + RAM |
| Hyperparameter tuning | Many GPUs |
| Evaluation | CPU/GPU |

**Hyperparameter tuning.** Test learning rate = 0.001, 0.01, 0.1; batch size = 32, 64, 128; layers = 2, 4. Cloud runs the experiments in parallel (GPU Job 1 with LR 0.001, GPU Job 2 with LR 0.01, GPU Job 3 with LR 0.1). Too many simultaneous experiments get expensive, so control the number of concurrent jobs, GPU allocation, maximum budget and job priority.

**Numerical [SG].** The grid is 3 x 3 x 2 = **18 combinations**. If each run takes 2 hours on 1 GPU:
- With 1 GPU: 36 hours.
- With 6 GPUs in parallel: 3 rounds x 2 hours = **6 hours**.
- With 18 GPUs: 2 hours, but the cost is 18 GPUs at once, which is why a budget cap is needed.

---

### T19. Inference resource management and load balancing

**Inference.** The service must maintain low latency (for example a prediction response under 100 ms), high throughput (for example 100,000 requests/sec) and high availability (the service continues even if some servers fail).

```
100,000 requests/sec --> Servers 1, 2, 3 --> Prediction
```

**Load balancing.** Incoming requests are distributed among the inference servers so that no server is overloaded.

```
          Users
            |
      Load Balancer
      /     |     \
 Server1 Server2 Server3
```

**Related PYQ:** MJ21 Q1(A)(VI) load distribution policy MCQ (Section 4).

### T20. Resource monitoring

**Definition.** Continuously observing how the resources of an ML system are used. What is monitored: CPU utilisation, GPU utilisation and memory, RAM, storage, network bandwidth and latency, number of requests, inference latency, error rate, active servers.

```
ML Application -> Resource Usage -> Monitoring System -> (CPU, GPU, Memory)
 -> Performance Analysis -> Take Corrective Action
```

**Why necessary (slide 69).** Of 10 GPUs, GPU1 is at 95%, GPU2 at 92%, GPU3 at 90%, GPU4 at 15% and GPU5 at 10%. Monitoring reveals the imbalance so workloads can be redistributed.

**Example (slide 72).** Normal 500 requests/sec rises to 5,000. Monitoring detects CPU 95%, GPU 98% and rising latency, so it triggers auto-scaling. If GPU utilisation is very high, more GPU instances start. If traffic falls, extra instances stop.

### T21. Cost optimization

Production ML needs GPUs, high-performance CPUs, large storage, high network bandwidth, many servers and cloud services. Goal: maximum performance with minimum unnecessary resource consumption.

**Five techniques:**

| Technique | Explanation and example |
|---|---|
| 1. Right-sizing | Allocate only what is required: needed 4 CPUs + 1 GPU, instead of 16 CPUs + 4 GPUs (prevents over-provisioning) |
| 2. Auto-scaling | Low demand 2 servers, high demand 10, demand drops 3 |
| 3. Remove idle resources | Release GPU/server when the job finishes |
| 4. Model optimization | Quantization, pruning, knowledge distillation, model compression: large model -> smaller model -> less memory + faster inference -> lower cost |
| 5. Efficient scheduling | Non-urgent training runs when resources are cheaper or more available; in high-demand periods priority goes to inference, in low-demand periods to large training |

**Numerical (slides 74, 80).**
- 20 GPUs x Rs 200/hour = **Rs 4,000/hour**.
- If monitoring shows only 10 GPUs are needed in low demand: 10 x 200 = **Rs 2,000/hour**.
- Utilisation case: 10 GPUs at 40% become 5 GPUs at 80%, for the same useful work at lower cost.
- **[SG] Daily saving:** 12 low-demand hours per day gives 12 x (4,000 - 2,000) = **Rs 24,000/day saved**, which is 25% of the Rs 96,000 daily cost.
- **[SG] Right-sizing waste:** allocating 16 CPUs + 4 GPUs when 4 CPUs + 1 GPU is needed means 12 CPUs and 3 GPUs (75%) are over-provisioned.

### T23. Workload prediction

**Definition.** Predicting the amount of computing work that will arrive in the future. Applied ML in cloud means learning patterns from historical cloud data to predict future workload, resource requirements, failures, errors or performance problems. Recent research stresses predictive (proactive) resource management over reactive rules only.

**Example.** A server gets 1,000 requests/min now. History shows traffic normally rises to 5,000 requests/min between 10 and 11 AM. The model predicts 4,800 requests/min in the next 15 minutes, so the system allocates resources **before** the rise.

**What can be predicted:** number of requests, CPU utilisation, memory utilisation, network traffic, number of VM/container instances required, storage I/O, response time, energy consumption, application workload, future resource demand. Useful for proactive autoscaling, resource provisioning, QoS management and energy optimisation.

**Architecture diagram:**

```
Cloud Applications
      |
Monitoring Data (CPU, RAM, Requests, Network)
      |
Data Preprocessing
      |
ML Model
      |
Predicted Workload
      |
Resource Manager
      |
Scale Up / Scale Down
      |
Improved Cloud Performance
```

The model keeps learning from historical and recent observations.

**Reactive vs proactive (slides 12, 13):**

| Without prediction (reactive) | With ML (proactive) |
|---|---|
| Workload increases | Historical data |
| CPU becomes overloaded | ML predicts workload increase |
| Performance decreases | Resources allocated in advance |
| Requests become slow | Workload arrives |
| SLA/QoS violation | Adequate resources available |
| Resources are added | Better performance |

**Numerical (slides 6, 7).**

| Time | Requests/min | CPU usage |
|---|---|---|
| 10:00 | 1,000 | 30% |
| 10:05 | 1,500 | 40% |
| 10:10 | 2,000 | 50% |
| 10:15 | 2,700 | 65% |
| 10:20 | 3,200 | 75% |

The notes' prediction: 10:25 with 3,800 requests/min gives approximately 85% CPU, so start more VMs/containers before CPU reaches a critical level. This is **predictive autoscaling**.

**[SG] Worked solution with simple linear regression** (x = requests in thousands, y = CPU %):
- mean x = 2.08 and mean y = 52.
- Slope = 64.7 / 3.148 = 20.55 % per 1,000 requests; intercept = 52 - 20.55 x 2.08 = 9.25.
- Prediction at x = 3.8: 9.25 + 20.55 x 3.8 = **87.3%**, close to the notes' ~85%.
- This shows the regression idea: the model learns the relationship between workload and resource usage.

**[SG] Time-series example (slide 11):** 1000, 1200, 1500, 2000 requests, then 10:20 = ?. The increments are 200, 300, 500, so the growth is accelerating. A plain average-increment estimate gives about 2,333, and repeating the last increment gives about 2,500. An LSTM can learn such non-linear trends from the sequence.

### T28. Example research problem and evaluation metrics

**Research problem:** "Machine Learning-Based Workload and Failure Prediction for Proactive Cloud Resource Management." The objectives are:
1. Collect cloud monitoring data.
2. Preprocess the historical data.
3. Train a workload-prediction model.
4. Predict future CPU/memory/request demand.
5. Train a separate failure-prediction model.
6. Integrate the predictions with autoscaling.
7. Compare with traditional threshold-based scaling.
8. Measure performance.

**Metrics:**
- *Workload prediction:* MAE, MSE, RMSE, MAPE, R2.
- *Failure prediction:* accuracy, precision, recall, F1-score, ROC-AUC, false-positive rate, false-negative rate.

**[SG] Formulas and worked examples.**

Regression metrics:
- MAE = (1/n) sum |y - y^|
- MSE = (1/n) sum (y - y^)^2
- RMSE = sqrt(MSE)
- MAPE = (100/n) sum |(y - y^)/y|
- R2 = 1 - SSres/SStot

Example: actual = 1000, 1200, 1500 and predicted = 950, 1250, 1450. The errors are -50, +50 and -50.
- MAE = 50
- MSE = 2,500
- RMSE = 50
- MAPE = (5% + 4.17% + 3.33%)/3 = **4.17%**
- R2: mean = 1233.3, SStot = 126,667 and SSres = 7,500, so R2 = 1 - 0.0592 = **0.941**

Classification metrics (from a confusion matrix with TP = 40, FP = 10, FN = 5, TN = 45):
- Accuracy = (40 + 45)/100 = **0.85**
- Precision = 40/50 = **0.80**
- Recall = 40/45 = **0.889**
- F1 = 2PR/(P + R) = **0.842**
- FPR = 10/55 = **0.182**
- FNR = 5/45 = **0.111**

Practical point for failure prediction: a high false-negative rate means missed failures (outages), while a high false-positive rate means wasted preventive actions and cost.

### Q1. Compare scalability and elasticity (D22, 5M)

**Scalability** is the ability of a system to handle a growing workload by adding resources. It can be vertical (a bigger machine) or horizontal (more machines). **Elasticity** is the ability to automatically provision and de-provision resources in real time to match the current demand.

| Point | Scalability | Elasticity |
|---|---|---|
| Meaning | Capacity to grow to handle larger load | Capacity to grow **and shrink** automatically with demand |
| Time scale | Long-term, planned | Short-term, dynamic, real time |
| Direction | Mainly scale up/out | Both scale out and scale in |
| Trigger | Design or planning decision | Automatic monitoring and policy |
| Cost view | Pay for the larger capacity | Pay only for what is used (pay-per-use) |
| Example | Adding more servers for expected growth in users | Inference servers rise from 2 to 20 at peak and fall back to 5 |

**Link to ML.** A cloud ML inference service uses elasticity (auto scaling) to follow the traffic. Scalability allows it to eventually serve millions of users.

### Q3. Compare GPU and CPU chips (MJ21 Q2 OR, 10M)

The full question also asks about power efficiency, programmability, performance and MPP architectures. The core GPU vs CPU comparison is below.

**Diagram idea (draw two boxes):**

```
CPU                                  GPU
+----------------------+            +----------------------------------+
| Few powerful cores   |            | Hundreds-thousands of small cores|
| Large cache          |            | Small cache, high bandwidth      |
| Complex control logic|            | Simple control, SIMT             |
+----------------------+            +----------------------------------+
Low-latency, serial tasks           High-throughput, data-parallel tasks
```

| Aspect | CPU | GPU |
|---|---|---|
| Core design | Few complex, powerful cores | Many simple cores |
| Optimised for | Low latency, serial and branch-heavy tasks | High throughput, data-parallel tasks |
| Memory | Large caches | High memory bandwidth, small caches |
| Performance | Strong on general-purpose and sequential code | Much faster on regular parallel work such as matrix operations (deep learning) |
| Power efficiency | Lower performance per watt on parallel work | Higher performance per watt for parallel work, though total power draw is high |
| Programmability | Easy; mature tools and general-purpose languages | Harder; CUDA/OpenCL, explicit memory handling, parallel thinking |
| Strength | Flexibility, operating systems, control logic | Training and large-scale numeric work |
| Weakness | Limited parallelism | Poor at branching/serial work; needs data transfer from host |

**Trade-off summary:** GPUs give the best power efficiency and performance for parallel workloads but are harder to program. CPUs are easiest to program and best for irregular workloads. Modern clusters therefore use a hybrid CPU + GPU design.

**MPP part (answer briefly if asked):** [SG] massively parallel processing systems differ in processor selection (general-purpose CPUs only vs CPU + GPU hybrids), performance target (peak vs sustained), efficiency (performance per watt) and packaging constraints (power, cooling, density). GPU-accelerated designs reach high performance in less space and power than CPU-only designs. Check specific machine names and figures against your textbook before writing them.

### Q8. Basic principle of power management techniques; DVFS (D22 Q4(ii), 10M)

[SG] The wording of the "basic principle" can vary between textbooks. This is the standard answer.

**Basic principle.** Make power consumption proportional to useful work: avoid spending power on idle or under-used components by **reducing the activity or capacity of hardware when demand is low** (slow it down, put it to sleep, switch it off, or consolidate the work onto fewer machines).

**Techniques that follow this principle:** DVFS, switching off or sleeping idle servers, server consolidation by VM migration, power-aware scheduling, efficient cooling.

**DVFS = Dynamic Voltage and Frequency Scaling.** The processor's supply voltage and clock frequency are adjusted dynamically according to the workload.

**Why it saves power.** Dynamic power is roughly P = C x V^2 x f. Lowering the frequency allows the voltage to be lowered too, so power falls much faster than performance.

**Numerical [SG].** If frequency is halved and voltage is also roughly halved:
- Power becomes about (1/2)^2 x (1/2) = **1/8** of the original.
- The task takes about twice as long, so energy = power x time is about 1/8 x 2 = **1/4** of the original.

**How it helps cloud computing:**
- Hosts run at lower frequency during low load, saving energy and cooling cost.
- Schedulers run non-urgent or deadline-flexible VMs/jobs at a lower speed.
- It supports green cloud goals while meeting SLAs, but there is a trade-off in slower execution.

**Related MCQ (MJ21 Q1(A)(I)):** power-management layers in distributed platforms are the application layer, middleware layer, resource layer and network layer. The exception is the **session layer** (option c).

### Q9. Server consolidation as power management; hardware vs software techniques (ND21, 5M each)

**Server consolidation.** Moving workloads (VMs) onto fewer physical servers using virtualization and live migration, then switching off or sleeping the freed servers. It raises the utilisation of the servers that remain on and removes the idle power of the others, which is why it is a power-management strategy. This is the same idea as the notes' "10 GPUs at 40% become 5 GPUs at 80%".

**Hardware vs software techniques:**
